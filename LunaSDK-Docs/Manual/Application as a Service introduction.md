Application as a Service (AaaS) is a programming pattern that we use to develop most editor/tool applications using LunaSDK. The core principles of AaaS are:
1. We do not develop GUI application directly, we firstly write a **service** (aka a library) that provides all functions that we need to provide through our application.
2. The service exposes such functions using [[Frontend]], which is a [[Variants|Variant]] based interface. All function calls and results through the interface can be serialized, thus can be delivered by almost all stream-based media, including TCP, UDP, files, system pipes, shared memory, etc.
3. The GUI application is only a thin layer that connects to the service, it accepts user inputs and translates them to [[Frontend]] function calls. It then accepts messages from the service through [[Frontend]] and displays them to users.
4. The same API used by the GUI application is also provided to automation tools and AI agents (by using Model Context Protocol), so that they can perform specific tasks that would rather require human doing them manually.
Since function calls through [[Frontend]] can be transformed through any stream-based media, the service and the application that uses the service does not have to be in the same process, or even the same machine, and can be written using different programming languages, and developed using different frameworks. For example, a common practice is to develop a service using LunaSDK/C++ for best performance, and then develop a GUI application using web frameworks. The GUI application can then send function calls to the service and accept results using JSON-RPC 2.0, achieving both performance and developing convenience.

In general, the developer can choose one of the following architectures to develop a AaaS application:
1. Compile the service as part of the GUI application, the application manages the lifetime of the service. This is very similar to traditional GUI application development path, only that all functions calls to the service should be transferred through [[Frontend]] module. When putting the service and the application in the same process, the function calls and results can be transferred using [[Variants|Variant]] objects directly, avoiding all serialization/deserialization cost. The application can then choose to expose service functions to third-party scripts and AI agents through some form of in-application console or web socket connections.
2. Compile the service and the application as two separate programs. The service has its own process that will be run firstly before the GUI application, the GUI application then connects to the service using web socket, system pipes or some user-provided media. This method adds more communication cost compare to the first one, but comes with more benefits, for example, the service and the application can run in different machines, allowing for remote control and cross-debugging. Also, the service will not be affected when the application crashes, ensuring more data safety and reliability.
