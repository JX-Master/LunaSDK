## Functionality

The HTTP module provides a transport-independent message model for completely received HTTP requests and buffered HTTP responses. The model preserves protocol information that applications may need, including duplicate field lines, request-target bytes, query text, trailers, body bytes, protocol version, and the remote endpoint.

The current message model is used by [[HTTP Server]], but it does not perform routing, URL decoding, media-type decoding, JSON parsing, authentication, cookie processing, or application validation. Those policies belong to the consumer above HTTP.

Include the public API with:

```cpp
#include <Luna/HTTP/HTTP.hpp>
```

## Concepts

### Request

`HTTP::Request` represents one complete request after HTTP framing has been validated and removed. A request contains:

- `method`: the case-sensitive method token stored as `Name`.
- `target`: the request-target exactly as received on the request line.
- `path`: the path derived from `target` without percent-decoding or normalization.
- `query`: the part after the first question mark, without the question mark itself.
- `version`: `HTTPVersion::http_1_0` or `HTTPVersion::http_1_1`.
- `headers`: header field lines in received order.
- `trailers`: trailer field lines in received order for a chunked request.
- `body`: decoded content bytes. Chunk sizes and delimiters are not included.
- `remote_address`: the peer address accepted by the TCP listener.

`target`, `path`, and `query` are independent `String` values. The HTTP module does not interpret percent escapes, dot segments, character encodings, form data, or URI semantics. Applications must perform any required decoding after choosing the rules appropriate for their protocol.

The request object passed to a handler is valid only for that handler call. Copy or move the fields that must remain available after the handler returns.

### Header and trailer fields

`HTTP::Header` stores one field line as a `Name` and `String` pair. Received field names are validated as HTTP tokens, normalized to lowercase ASCII, and stored as `Name`. Field values are stored as `String` after leading and trailing optional whitespace is removed.

Headers and trailers use `Vector<Header>` rather than a map. Duplicate fields and received ordering are therefore preserved. Applications must apply field-specific combination rules themselves. A field that must occur exactly once should be checked for both absence and duplication before its value is used.

Field values may contain valid HTTP `obs-text` bytes and are not necessarily UTF-8. Do not pass an arbitrary field value to a Unicode parser without validating or decoding it according to the field's specification.

### Body

`Request::body` and `Response::body` use `Blob` because HTTP content is an arbitrary byte sequence. The server decodes HTTP chunk framing before constructing a request, but it does not decompress content encodings or parse media types.

An empty body and a zero-length body both produce an empty `Blob`. Consult application protocol fields such as the method and `content-type` when that distinction matters to the application.

### Response

`HTTP::Response` describes one final buffered response:

- `status_code` is a final status from 200 through 599.
- `headers` contains application response field lines.
- `body` contains the selected representation bytes.
- `close_connection` asks the server to close the connection after the response is sent.

The HTTP server owns response framing. Application-provided `content-length`, `transfer-encoding`, and `connection` fields are ignored, and authoritative fields are generated by the server. Other response field names and values are validated before serialization. Invalid response metadata produces an HTTP 500 response instead of emitting malformed or injected field lines.

Responses are serialized as HTTP/1.1. A response to `HEAD` does not send body bytes but reports the representation length. Status 204 sends neither content nor `content-length`. Status 304 sends no body bytes and reports the representation length.

## Programming guide

### Inspect the request target

Use `method` and `path` for ordinary dispatch. Treat the received target and query as encoded data until the application explicitly decodes them.

```cpp
HTTP::RequestHandler handler(
    [](const HTTP::Request& request) -> R<HTTP::Response>
    {
        if(request.method == Name("GET") && request.path.compare("/health") == 0)
        {
            HTTP::Response response;
            response.headers.push_back(
                {Name("content-type"), String("text/plain; charset=utf-8")});
            const c8 body[] = "ok\n";
            response.body = Blob(body, sizeof(body) - 1);
            return response;
        }

        HTTP::Response response;
        response.status_code = 404;
        return response;
    });
```

`path` is not security-normalized. A file-serving or authorization layer must define and enforce its own percent-decoding, separator, and dot-segment policy before mapping a path to a resource.

### Read one unique field

The following pattern rejects duplicate field lines instead of silently selecting one:

```cpp
const String* content_type = nullptr;
bool duplicate = false;
for(const HTTP::Header& header : request.headers)
{
    if(header.name != Name("content-type")) continue;
    if(content_type)
    {
        duplicate = true;
        break;
    }
    content_type = &header.value;
}

if(duplicate)
{
    HTTP::Response response;
    response.status_code = 400;
    return response;
}
```

Other fields intentionally allow multiple lines. Iterate the vector in order and implement the rules defined for that specific field rather than applying one global combination policy.

### Process request content

Check the appropriate application metadata before interpreting `body`. For a protocol that requires JSON, validate `content-type`, then pass the exact byte range to the selected JSON codec.

```cpp
const void* bytes = request.body.data();
usize byte_count = request.body.size();
// Decode bytes according to the application protocol.
```

The request body may contain embedded zero bytes and is not null-terminated.

### Construct a response

Add application fields and body bytes to a default response. Do not calculate or add `content-length`; the server does that after the handler returns.

```cpp
HTTP::Response response;
response.status_code = 201;
response.headers.push_back(
    {Name("content-type"), String("application/octet-stream")});
response.headers.push_back(
    {Name("cache-control"), String("no-store")});
response.body = Blob(output_data, output_size);
return response;
```

Set `close_connection` only when the application needs to end an otherwise persistent HTTP/1.1 connection after this response:

```cpp
response.close_connection = true;
```

The HTTP module provides no response streaming in this revision. The complete response body must be available when the handler returns.
