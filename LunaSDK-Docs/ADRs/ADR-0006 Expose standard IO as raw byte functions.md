## Background
The Runtime module currently exposes standard input and standard output through one process-global `IStream` returned by `get_std_io_stream`. The implementation does not behave like an ordinary byte stream: reads stop at a newline, discard that newline, preserve incomplete UTF-8 characters internally, and append a null terminator; writes interpret the buffer as UTF-8 text and stop at the first null byte. On Windows, Runtime initialization also changes the process console input and output code pages.

These behaviors make the API unsuitable for framed transports such as the Model Context Protocol standard IO transport. Such transports need every byte, including newlines and embedded null bytes, to pass through unchanged. Combining input and output in one `IStream` also omits standard error and suggests an object identity and lifetime that do not exist: the three standard streams are process-global resources owned by the host platform.

The replacement must provide transparent byte transfer, preserve standard input/output/error separation, observe standard-handle replacement performed after Runtime initialization, work with terminals, pipes, and redirected files without a public device-classification API, and avoid changing process-wide terminal configuration.

## Decision
Replace `get_std_io_stream` with three Runtime functions:

```cpp
RV read_standard_input(void* buffer, usize size, usize* read_bytes = nullptr);
RV write_standard_output(const void* buffer, usize size, usize* write_bytes = nullptr);
RV write_standard_error(const void* buffer, usize size, usize* write_bytes = nullptr);
```

Each function performs one blocking native I/O operation on the standard handle current at the time of the call. On POSIX platforms the functions use file descriptors `STDIN_FILENO`, `STDOUT_FILENO`, and `STDERR_FILENO`; on Windows they fetch the corresponding handle with `GetStdHandle` for every operation and use `ReadFile` or `WriteFile`. Consequently, redirection performed with facilities such as `dup2` or `SetStdHandle` after Runtime initialization is observed by later calls.

The buffers are untyped byte ranges. The functions do not interpret or validate UTF-8, do not add or search for null terminators, do not add, remove, or translate newlines, and do not change console code pages or modes. A zero-size operation succeeds with zero transferred bytes without accessing the buffer. An input end-of-file succeeds with zero bytes read. Native short reads and short writes are reported through the optional byte-count parameter and are not converted into errors; callers that require an exact byte count must repeat the operation.

The functions may be called concurrently, but Runtime does not serialize calls and does not define the ordering of bytes produced by concurrent writers. Standard-handle replacement must be synchronized by the application against active I/O calls.

Writing to a closed pipe reports `E_BAD_PIPE` instead of terminating the process. The POSIX implementation suppresses only the `SIGPIPE` generated by its own write operation without changing the process-wide signal disposition. Other native failures are translated to Runtime errors. Standard output and standard error remain independent so a protocol can reserve standard output for framed messages and direct diagnostics to standard error.

`get_std_io_stream` and its boxed stream implementation are removed. Runtime and platform initialization no longer create standard-I/O objects, mutexes, UTF-8 carry buffers, or console-code-page state. Existing callers must choose input, output, or error explicitly and must pass the intended byte count rather than relying on null termination.

No public `get_standard_stream_device` function is introduced. Device classification is not needed for raw transfer, differs across platforms, becomes stale if a handle is replaced, and would encourage check-then-act logic. A future terminal-specific feature may introduce narrowly scoped terminal-query or text functions if a concrete use case requires them.

## Impact
MCP and other framed transports can use Runtime standard I/O without a custom codec path or platform-specific handle access. Embedded null bytes, newline-delimited headers, partial UTF-8 sequences, and arbitrary binary payloads are preserved. Applications can keep protocol output isolated from diagnostics by using standard output and standard error separately.

The change breaks source compatibility for callers of `get_std_io_stream`. The current repository caller, LunaDoc, must migrate to `write_standard_output` and exclude its C string terminator explicitly. External callers that need an `IStream` must provide an adapter appropriate for their protocol and buffering requirements.

Because one call mirrors one native operation, callers must handle short transfers. Concurrent writes may interleave according to platform behavior. On interactive Windows consoles, byte interpretation remains controlled by the console and its current mode/code page; Runtime no longer imposes UTF-8 process-wide. Higher-level terminal text conversion is outside this API.

## Alternatives considered
### Keep and repair the combined `IStream`
This was rejected because one bidirectional object still conflates standard input and standard output, cannot represent standard error, and implies object ownership and identity for process-global platform resources. `IStream::write` also normally promises complete writes, while exposing native standard-handle behavior is more useful for transport code.

### Expose three interface objects
This would separate the streams but adds reference counting, object lifetime, interface dispatch, and three singleton identities without enabling multiple instances or ownership. Direct functions express the process-global model more accurately and avoid needless allocation and dispatch.

### Expose a stream-device classification function
This was rejected because raw I/O does not require classification, platform categories are not uniform, and the result can become stale immediately after standard-handle replacement. Terminal-specific policy should be introduced only with a corresponding terminal feature.

### Retain text-oriented behavior behind configuration options
This was rejected for the base API because text decoding, line reading, newline policy, and terminal presentation are higher-level concerns. Making them options on raw operations would complicate transport behavior and recreate the ambiguity of the old API.
