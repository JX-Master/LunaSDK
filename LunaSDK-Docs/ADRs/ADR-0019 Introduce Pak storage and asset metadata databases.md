## Background
Shipping a game as loose files increases deployment cost. A single package should represent a directory tree, support read-only and editable use, and defer physical writes until explicit flush or VFS unmount/shutdown. Asset discovery should read one metadata database instead of opening many `.meta` files.

These requirements cross three separate domains. VFS routes file operations between storage devices. Asset manages logical assets, including GUIDs, types, shared paths, and multiple data units. An archive is a general container of files and directories and must not depend on either domain. ADR-0018 supplies the independent Zip module used by this decision; ADR-0014 defines the asset records that the database must preserve.

Before this change, VFS had driver callbacks and an error-returning unmount operation, but no device flush operation. Its module shutdown cleared mounts without calling their unmount callbacks. Runtime `IFile::flush` and module shutdown return no error. Current Asset metadata loading, saving, moving, and copying directly assume per-asset JSON `.meta` files. Adding only a package reader or a second discovery function would not address these lifecycle and persistence assumptions.

## Decision
Treat Pak storage, VFS integration, and Asset metadata databases as one architecture delivered in stages under this ADR. The standalone Pak, VFS integration and Asset database stages are implemented with documentation and tests. All stages update this ADR's delivery record rather than introducing separate competing architectural decisions.

### Module responsibilities
| Module | Responsibility | Dependencies relevant to this feature |
| --- | --- | --- |
| Zip | Standard ZIP/ZIP64 parsing, archive edits, codecs and checksums | Runtime, libzip; libzip uses zlib |
| Pak | Validated directory tree, seekable file handles, staged file writes, repeatable flush | Runtime, Zip |
| VFS | Filesystem instances, path routing, mount references, storage publication, unmount/shutdown | Runtime, Pak |
| Asset | Asset records and database implementations over ordinary VFS files | VFS and existing serialization facilities |

Pak does not define asset GUIDs, loaders, data units, `.meta` files, database filenames, or mount points. Applications can use Pak directly with arbitrary seekable streams. VFS mounting does not implicitly register assets. Application code first mounts storage, then opens/imports the appropriate Asset database through its VFS root.

### Package representation and paths
A phase-one `.pak` is a standard single-volume ZIP/ZIP64 archive with a validated filesystem naming profile. There is no mandatory private header, asset manifest, or reserved file. Ordinary ZIP tools can inspect it, and compatible ordinary ZIP archives can be opened as packages.

Store and Deflate are supported in the first phase. Creation accepts a default compression selection for new files; Store is the default. Individual files may override it. Existing files preserve their method unless explicitly changed. The default is a session policy, not a hidden package entry. Encryption and other codecs are rejected explicitly during package opening. Future codecs/encryption use ZIP method identifiers, flags and extra fields through Zip, with Pak defining their file-access policy. A format revision is required before adding semantics that existing readers must not silently ignore.

Paths are UTF-8, case-sensitive and slash-separated, with no Unicode normalization. Imported names are decoded by Zip/libzip before Pak validates and indexes them. The package has an implicit root and synthesizes parent directories missing from the ZIP directory. Duplicate explicit paths, file/directory collisions, non-empty directory entries, absolute ZIP entry names, empty/dot/parent components, backslashes and drive-style colons are rejected. Public operations accept an optional leading slash and a directory trailing slash; the empty path and `/` identify the root. No symbolic-link resolution or host filesystem permission interpretation is performed. ZIP entries marked as links by external attributes are ordinary file bytes here.

Opening scans the ZIP central directory and builds a memory index. It does not decode file payloads. Zip's bounded archive-tail reads may overlap payload bytes while locating structural records, so this is not a guarantee that every physical read lies exclusively in metadata.

### File operations and staging
Pak exposes Runtime file access/creation modes, file attributes, directory iteration, directory creation, file copying, subtree moves, and deletion. Parents must exist before creation. Copy operates on a file; deleting a directory requires it to be empty. Directory iteration is a sorted snapshot. ZIP timestamps and external attributes are not part of the phase-one Pak API; Runtime timestamp fields are zero.

Read-only files are decoded on demand through Zip, with independent logical cursors. Seeking forward skips decoded bytes; seeking backward reopens and replays decoding. This keeps read-only memory bounded but does not promise constant-time random access, even for Store with the current Zip interface. Reading through EOF verifies the ZIP CRC; a partial read does not validate unread data.

Writable opening materializes that file into a private seekable staging stream, unless its contents are being discarded. The default staging stream uses memory, with a configurable per-file limit (256 MiB initially). Applications can supply a staging-stream factory backed by temporary files or other storage for larger editable files. The limit applies to the built-in memory implementation, not to read-only decoding or custom staging. Extending a file zero-fills the gap. Staging never writes the source package.

A file permits multiple readers or one exclusive writable handle. Operations affecting an open file, and moves of a subtree containing open files, return `E_BUSY`. Other files remain editable. Handles retain their package; directory snapshots do not block mutations or flush. Operations on one package and its handles are serialized by a package mutex. Separately opened packages sharing the same underlying stream still require caller synchronization. Staging callbacks must not reenter the package or return aliased storage.

### Repeatable flush and error handling
`IPak::flush(destination)` writes a complete package to a distinct readable, writable, seekable and resizable stream. All package file handles must be released first. The output must not alias the current source or any retained staging stream, including through separate handles. Pointer-identical aliases are rejected. Output contents are replaced; input contents remain unchanged.

Pak retains its own directory and staged data independently of Zip's editing session. Flush opens a separate Zip edit session over the current source, applies changes, saves, and reopens the output before adopting it as the new source. Surviving unchanged ZIP entries can be copied without decoding/recompression. This isolates Pak from Zip's consuming save operation and allows repeated edit/flush cycles on the same Pak object.

On failure, Pak keeps its previous source, pending changes and dirty state for retry; the destination may be incomplete, or complete if reopening failed. On success, it releases old sources/staging, adopts the destination, and clears dirty state. Flushing an unchanged editable package still writes a complete output. A newly created empty package is dirty until first flush. Read-only packages reject flush. Explicit discard closes the package without writing, and ordinary destruction also discards pending changes.

This is stream serialization, not filesystem publication or durable synchronization. It deliberately takes an output stream rather than overwriting a source that libzip is still reading. Native namespace replacement is handled by VFS through Runtime `move_file` with explicit flags; arbitrary streams still have no generic transactional publication primitive. `IFile::flush` cannot report synchronization failures.

### VFS integration stage
Expose a reference-counted `IFileSystem` representing an already-created filesystem instance. It supplies file access, attributes, directory iteration, directory creation, copying, moving, deletion, native-path translation and error-returning `flush()`. Its paths are relative to the instance root; the empty path names that root. Concrete filesystem implementations can be used directly without a VFS mount.

VFS mounts an instance with `mount(IFileSystem*, mount_path)` and retains it. There is no driver-name registry, `DriverDesc`, mount callback, or erased `params_type`/`params_data` object. Runtime reflection still identifies interfaces and objects, but is not a VFS driver registry. Native instances are constructed by `new_native_file_system(native_path)`. Pak instances are constructed by `new_pak_file_system(native_path, mode, options)` or its `IPakStorage*` overload. Factories validate and resolve storage before mounting; mount only attaches an existing instance to a namespace.

A filesystem can be mounted at multiple paths. These aliases share data, access mode, publication state and file-handle constraints. Copy/move methods accept an optional destination instance; null selects the source instance. VFS offers the operation to the source instance first. Native instances preserve native copying and file/directory moving across native roots. Pak handles operations within one instance, including between aliases. Implementations return `E_NOT_SUPPORTED` without side effects for unsupported combinations, selecting bounded streaming of file bytes. Fallback moves copy then delete and do not provide a multi-device transaction; this generic path copies files only. Concrete implementations recognize compatible destination objects without a router-owned driver registry.

A specific filesystem is saved by calling `IFileSystem::flush()` directly, without resolving a mount path. Remove `VFS::flush(mount_path)`. Retain `VFS::flush_all()` for application-wide saving; it visits each distinct mounted instance once, attempts all instances and preserves the first failure's diagnostic. Native filesystem flush has no deferred device-level work. Pak flush requires all of that instance's file handles to be released, whether opened through VFS, another mount alias or the instance directly. Directory snapshots do not block Pak flush. File-handle `flush()` only flushes staging and does not publish the package.

Checked unmount requires that mount's VFS files and directory iterators to be released, then calls the instance's flush. Failure keeps the mount available for retry. Success removes only that mount's reference; it does not close or invalidate the filesystem instance. External references and other mounts may continue using it or mount it again. Ordinary instance destruction releases storage and discards any unsaved changes; applications using instances without mounting explicitly flush before releasing them.

Pak retains its storage provider, package and pending publication in the filesystem object. Clean and read-only instances need no serialization or publication. Serialization failure preserves the original input and staged edits. Publication failure retains the completed output; reads remain available while new edits return `E_BUSY`. Retry publishes the same output without recompressing. Instance-level synchronization and file-handle accounting also guard direct flush and pending-publication retry; mount bookkeeping is not the authority for Pak persistence.

`IPakStorage` supplies `open_source`, `create_output` and `publish` for application-owned streams. The instance retains the provider. The provider owns publication and output cleanup; writable instances require exclusive control of backing storage, including aliases through other paths or objects. Providers and filesystem methods invoked by VFS must not reenter VFS. Provider callbacks must not reenter their owning filesystem or mutate a retained input.

Runtime uses one `move_file(from, to, FileMoveFlag flags = FileMoveFlag::none)` API for ordinary moves and replacement. `allow_overwrite` permits replacing an existing file; existing directories cannot be overwritten, and a directory cannot replace an existing file. Moving a directory to an absent destination remains supported with either overwrite setting. `no_copy` independently forbids native cross-volume copy/delete fallback. The default preserves existing calls: no overwrite, with Windows permitting cross-volume file copying and POSIX requiring a native rename. Keeping these flags independent preserves ordinary move behavior while making Pak publication's stronger requirement explicit. Source and destination must identify distinct files or directories, and callers must exclude concurrent namespace changes.

For native packages, serialize to a sibling temporary file and publish through Runtime `move_file(from, to, FileMoveFlag::allow_overwrite | FileMoveFlag::no_copy)`: POSIX `rename` or Windows `MoveFileExW` with `MOVEFILE_REPLACE_EXISTING`, without cross-volume copy fallback. See the [Apple rename reference](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/rename.2.html) and [Microsoft MoveFileExW reference](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw). A reopenable stream closes native handles for replacement while preserving the adopted stream's identity, size and logical cursor. Failed serialization cleans up incomplete outputs. Failed publication preserves the complete temporary file and reports its path. Namespace replacement does not promise physical-media durability.

VFS shutdown first invalidates/releases all VFS-owned file and iterator wrappers, then flushes each distinct instance once and releases the mounts. Failures are logged because module shutdown cannot return errors. VFS does not close caller-owned filesystem objects or direct handles, and has no unmount/force-unmount callbacks. A caller-owned Pak file still open at shutdown can therefore cause `E_BUSY`; applications must release direct handles before checked flush/unmount or shutdown. Failed publication outputs follow the storage provider's retention policy; complete native outputs remain available for recovery.

Path routing selects the longest matching mount prefix in the same root and absolute/relative namespace; remount rejects occupied destinations. VFS wrappers coordinate mount lifetimes. Concrete instances own synchronization of their direct operations; Pak serializes its own operations and file handles. Native handles remain ordinary Runtime files. VFS retains its global routing/device-operation lock, and instance methods used by VFS must not call back into the router.

### Asset database stage
Implement this stage through a pure-virtual `IAssetDatabase` interface and typed factories for sidecar and single-file databases. Both implementations use ordinary VFS APIs and existing serialization facilities. Database records contain a GUID, a relative path, a type and named data-unit descriptors. Database objects can be used independently by conversion tools; registration attaches one retained database to the Asset registry. Registered databases have nonoverlapping roots, and callers must keep their VFS bindings stable. Direct mutation/reload of a registered provider is reserved for Asset's coordinating operations.

Database snapshots separate external reads from registry publication. Read and validate a complete candidate snapshot before reconciling entries; reserve affected entries during commit so active data-unit operations cannot invalidate validation. Registration and reload reject duplicate paths/GUIDs, ownership conflicts and changes incompatible with loaded units without partially changing the registry. Reload rejects dirty databases. Unregistration requires unloaded idle assets and a successful checked database flush; handles remain unregistered placeholders. Legacy paths outside explicit database roots continue using sidecars.

Single-file databases stage record changes in memory, and database flush writes JSON through VFS to a sibling temporary file before replacing the database. Sidecars preserve immediate per-record saves using the same replacement helper. Extend `FileMoveFlag` through VFS and Pak moves; `no_copy` forbids the router's streaming fallback, and replacement fails without deleting the destination when unsupported. Pak validates all affected entries and handles before changing its staged namespace. No Asset implementation accesses native paths or imports Pak/Zip.

Conversion exports a validated relative-path snapshot from an independent source database into a newly created single-file database, preserving GUIDs and named units. It copies metadata only and never deletes source sidecars; callers copy the selected payload files separately. A database file and reserved metadata temporary files are excluded from generic asset payload maintenance.

One centralized database covers a specified root and its complete descendant tree, as selected by the user. For example, `/Assets/assets.db` contains records whose asset paths are relative to `/Assets`. The main data unit remains implicit in the asset type. The JSON database has its own `format_version` of `1` and an `assets` array, with GUIDs encoded through Runtime's existing `[low, high]` unsigned 64-bit representation. Sidecars continue reading versions 1 and 2 and writing version 2. The filename is configurable and is an ordinary file to VFS/Pak. Records and named units are sorted on output; in-memory indexes support GUID/path lookup.

Opening a centralized database reads and validates the one database file without registering assets. Explicit registration resolves paths beneath the chosen root and installs records from the logical snapshot without reading payload files or scanning for `.meta` files. When stored in Pak, the database itself is a file payload that must be read; the requirement is to avoid decoding the other asset payloads. The same database works in a normal directory.

Database roots have explicit ownership: reject overlapping registered roots initially. An explicitly selected database is authoritative within its root; do not silently merge sidecars and centralized records, or fall back to scanning after a corrupt database. Validate versions, relative paths, duplicate GUID/path mappings, record contents and existing-registry conflicts before applying a batch. Metadata updates retain the existing busy/loaded data-unit checks. Metadata failure must not leave a partially registered batch.

Route metadata load/save and asset create/move/copy/delete through the selected database. A discovery-only second API is insufficient because the existing maintenance operations unconditionally write or move `.meta` files. In centralized mode, metadata save updates a database record and database flush writes the file; generic asset file enumeration must not treat that shared file as one asset's payload. Moves across database roots transfer the record through both providers and report partial physical-operation failures; no global filesystem transaction is implied. Sidecar mode preserves the existing developer workflow and old metadata compatibility.

Conversion is an explicit tooling operation: collect and validate sidecar records, write the centralized database, verify it, and only remove sidecars when explicitly requested. Packaging can leave source sidecars untouched while emitting only the database and payload files. Database authority is never inferred solely from a `.pak` extension.

### Persistence order across the layers
Applications save asset data units and metadata records, flush the Asset database into ordinary VFS files, release file handles, then flush/unmount the VFS device. For Pak, database and asset file updates are then serialized into the same package output. Closing Asset precedes closing VFS, which precedes Pak/Zip dependencies. VFS never calls back into Asset to discover pending metadata. Checked application shutdown must follow this order; Pak cannot save Asset changes that were never written to its files.

## Impact
Applications gain ordinary filesystem operations on a single archive without depending on VFS or Asset. Asset databases remain usable on any mounted filesystem, and ZIP tools remain useful for inspection and interoperability. No additional third-party dependency is required beyond the setup-managed Zip dependencies.

An archive flush is proportional to the resulting package size and is not an append journal or block transaction. Read-only compressed seeking can be expensive; writable files require staging proportional to their uncompressed size. Custom staging limits memory use but adds application storage responsibilities. Block compression, encryption, extraction, background compaction, filesystem permissions and crash-durable generic stream transactions are outside the first stage.

VFS replaces driver registration and parameter-erased mounting with retained filesystem objects, typed factories and instance flush. Callers must migrate and rebuild; no compatibility driver registry is retained. Instance identity determines shared-state operations; compatible implementations may handle cross-instance copies/moves directly, with generic streaming as fallback unless `no_copy` forbids it. VFS depends on Pak/Zip, so its builds require the setup-managed libzip/zlib source SDKs. Existing sidecar workflows remain supported. Centralized Asset mode routes discovery and maintenance through providers and requires explicit flush ordering. `get_asset_files` now lists payload files only; metadata files are owned and maintained by the provider.

Existing move callers remain source-compatible through default flags arguments, but consumers must rebuild for changed Runtime, VFS and Pak function signatures. Custom `IFileSystem` implementations must accept the new move flags and implement their semantics or return `E_NOT_SUPPORTED` without mutation. The separate Runtime replacement API is removed; its callers use `allow_overwrite | no_copy`. Zip entry-data replacement is a separate operation and retains its own interface.

## Alternatives considered
### Retain the driver registry and expose an instance wrapper
Keeping both construction mechanisms would preserve erased mount parameters and duplicate the ownership model. Direct instance factories make construction, references and explicit flush usable independently of routing. Driver registration and mount lifecycle callbacks are removed rather than wrapped.

### A private binary Pak format
A private format could optimize block access and incremental commits, but would add format tooling and validation work before those requirements are demonstrated. Standard ZIP/ZIP64 plus a strict directory profile satisfies the current scope and already supports codec extension identifiers.

### Asset records in the ZIP central directory
This would couple general archive storage to logical assets and prevent the same metadata implementation from working in loose directories. A normal database file keeps the responsibilities separate.

### Expose Zip directly as the VFS driver
Zip has entry-level edits, sequential readers, nonrecursive directory markers and a consuming save. A Pak layer provides the file semantics, tree validation and repeated flush lifecycle that a VFS driver needs, and makes those capabilities reusable outside VFS.

### Buffer the entire archive or overwrite it in place
Whole-archive buffering scales with package size. In-place generic stream rewrites can destroy source bytes still needed for a flush and cannot promise recovery. Separate destinations and per-file staging give explicit ownership and retry behavior.
